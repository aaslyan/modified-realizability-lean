The anatomy of an extracted function

A constructive proof of Fibonacci, taken apart. Underneath the machinery is the two-variable loop you already know — and above it, something stranger.

read straight off the proof term · n = 0,1,2,3
(0, 1) → (1, 1) → (1, 2) → (2, 3)

Both halves of the extracted realizer, evaluated. This is not an analogy for the iterative Fibonacci — it is the loop's exact running state, falling out of a proof that never mentions a loop.

the loop you already know

Everyone has met this Fibonacci

Its entire memory is a pair (a, b); each step slides the window one place forward. Hold on to the pair — it is the whole story.

# the classic two-variable iteration
a, b = 0, 1
repeat n times:
    a, b = b, a + b
return a
the paired invariant · ordinary induction

The same idea, written as a proof

The proof never speaks of a loop. It proves a statement — and the statement carries the very same pair as its invariant. The inductive step is the window slide: from (y, z) it witnesses (z, y + z).

def fibPairedTheorem :
  Deriv [] (∀n. (∃y. fib n = y) ∧ (∃z. fib (n+1) = z))

-- proved by ordinary `ind`, no ordinals, no strong induction
-- step:  given (y, z),  supply the witnesses (z, y + z)
-- lvl = 1   → realizers live in PureType 2
the extracted term

It really is a λ-term

Modified realizability reads a program off that proof, one rule at a time. ind becomes a recursor; each ∃ becomes a pair ⟨witness, evidence⟩; application and abstraction are app₁ / abs₁ — and their computation rule is β-reduction, on the nose.

extract (ind base step) = indC (extract base) (extract step)

indRecC seed step 0     = seed                        -- ⟨0, 1⟩
indRecC seed step (k+1) = app₁ (app₁ step k) (indRecC seed step k)

app₁ (abs₁ G) x = G x                                -- β, a proved theorem
both witnesses, evaluated

Watch the loop fall out

Read the two existentials' witnesses at each n and the pair-state tumbles out — the same (a, b) climbing the same ladder. Every operation in the running term is +; the word fib appears only in the specification it satisfies. This is a real, build-checked line in the source.

#eval (List.range 4).map (fun k => (fibonacci k, fibNext k))
⟹ [(0, 1), (1, 1), (1, 2), (2, 3)]

theorem fib_pair_spec (n) :
  (fibonacci n, fibNext n) = (fibN n, fibN (n+1))   -- checked, every n
#print axioms fibonacci  ⟹  [propext, Quot.sound]      -- no choice
PureType 2 · Continuous2

Step back: it is a functional of functions

The object is not a number-cruncher. It takes functions to numbers — a genuine type-2 object — and it is continuous: a Kleene–Kreisel continuous functional, certified for free by the pipeline's generic continuity theorem.

extract fibPairedTheorem ρ [] 1  :  PureType 2

theorem fib_extract_continuous (ρ) :
  Continuous2 (extract fibPairedTheorem ρ [] 1)
CtQ 2 · the extensional object

And then it collapses

Quotient by extensional equality and the term lands in CtQ 2. Here is the fantastic part: any proof of the theorem — a different derivation, a different λ-term — collapses to the same element. The program's identity stops depending on how you proved it.

Nothing here is hand-waved

The extract genuinely runs — it is ordinary induction, not transfinite — but it re-evaluates its pair without sharing, so the cost is exponential in n. So the headline fibonacci 10 = 55 is delivered certified, by rewriting through fibonacci_spec to the kernel-checked fibN 10 = 55 — proved, not evaluated.
